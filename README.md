# 雨洪安置点 · 物资套餐的共需分析

清桥应急中转库由 12 位值班员服务青堤河西岸的安置点。各点以电话、纸质单和群消息报户数与物资。值班员过去抄进共享表后人工挑常同报的物资成套，碰到重复来单、未核单混入统计、各组同时备货挤占应急保留库存，难以解释调度结果。应用串联现场来单、核单、共需筛选、整箱起草和出库凭证，把库房台账交给下游搬运与点位领用负责人。

| 角色 | 主要页面 | 权限 |
| --- | --- | --- |
| operator | 安置点需求、共需搭配、整箱筹备 | 登记带户数的需求明细、冻结并分析已核单样本、起草整箱配发、搁置草案 |
| reviewer | 安置点需求、共需搭配、出库复核 | 核对来单、运行分析、复核并批准出库或搁置 |
| viewer | 四页 | 查阅来单、分析历史、装箱口径及库存与出库记录 |

## 一天的库房交接

1. 08:10 青堤河西岸建立响应 F-1123，清桥应急中转库先核西河小学等 8 份来单。南堤文化站 QA-W09 新送到，仍等确认。
2. 09:30 值班员冻结 8 个已核单样本。把物资按是否申报构造成来单集合，不把同一单的多件物资重复计数。
3. 09:40 Eclat 得到隔潮睡垫和保温毯在 4 单共同出现。两项各出现 5 次，支持度 50%，双向置信度 80%，提升度 1.28。
4. 10:00 整箱筹备显示一个搭配为 6 件隔潮睡垫加 4 件保温毯。运输按箱装，库存仅 4 套可配。
5. 10:15 西河小学 QA-W01 与运河礼堂 QA-W02 各起草 3 套。草案只是申请，留存实际需求单及搭配场次。
6. 10:25 第一张草案获批，库存相应减少 18 件隔潮睡垫和 12 件保温毯。第二张批准时只剩 1 套可配，系统拒绝侵占应急保留量。
7. 10:30 值班员搁置第二张三套草案，并注明库存原因。需要时可按 1 套重起。旧单及其处置仍可查。
8. 10:45 仓库下一班查看整箱结余、批准与搁置凭证以安排交接。

演示启动已有一次共需场次及一条 2 套草案，回归用例另起两张有竞争的草案实测并发。当前部署只有一个响应，业务数据按响应分区。

## 计算口径

每个已核单凭证代表一个篮子。分配 ID 给物资，在后端建「物资 → 需求单 ID 集合」的垂直索引。两个集合的交集大小 `AB` 是共同出现次数，去重后的分析窗为 `N`。支持度 `AB/N`，从 A 到 B 的置信度 `AB/A`，反向 `AB/B`，提升度 `AB*N/(A*B)`。实现计算 Eclat 到深度二，适合按双箱打包的库房。支持度和提升度低于所选门槛的组合不返回。样本少于四份拒绝计算，待核单不在冻结 ID 内，新确认样本仅进入后续场次。共需说明历史篮子关系，出库另检查实际申请与库存。

配发核验用整箱件数乘套数，与同一需求单减已出库量后的余额比较。可用量为库存扣除保留。审批先锁定响应，再同时复查两项余额、更新库存、写出库凭证。并发更新会串行检验，任何一个物资不足都不扣两项库存。

## 已核需求单的更正

复核员可对已核需求单改写物资件数并附更正原因，系统保留更正前后的明细与经办人。更正保存时，所有把该单列入冻结样本的共需场次（含仍在计算的）立即停用，停用原因与时间可查，旧搭配结果仅作历史查阅。旧搭配关联的待批草案随即停用，由这些搭配发起的换品同意也一并作废，不能再用于出库；已批准的出库凭证与点收记录保留原样。

每个场次冻结样本时记录各单的更正版本号。更正后系统按原门槛生成替代场次重算，结果为「只启用纳入最新更正的那一版」。重算失败可再按原门槛重试；停用状态不因重算或重试而恢复。若更正与重算并发，后台任务在计算前比对冻结时的版本号，发现样本已被更新的更正改动，则丢弃本次任务并保持场次停用，晚完成的旧任务同样如此处理。共需页面展示停用原因、停用前旧结果及指向替代场次的入口。

## 启动与开发

```bash
cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

[前端](http://localhost:18290) · [API 文档](http://localhost:19290/docs) · PostgreSQL 宿主端口 17790。演示账号 `operator@demo.local`、`reviewer@demo.local`、`viewer@demo.local`，密码统一为 `Demo2026!`。

| 服务 | 技术与代码 |
| --- | --- |
| frontend | Nginx 同源转发，原生 ES modules，`depot.js` 四个业务页面 |
| backend | FastAPI/Pydantic，`domain.py` 路由，`dispatch.py` 管理核单、分析、草案和审批 |
| worker | Python 执行冻结样本的 Eclat 交集分析，算法在 `eclat.py` |

| redis | Worker 依赖与健康探测 |

开发迭代用 `docker compose up -d --build frontend backend worker`。环境变量和覆盖端口见 `.env.example`。已核单状态、共需场次状态、配发阶段定义于 `backend/schema.sql`，后端状态跳转见 `backend/dispatch.py`，前端枚举 `requestPhase`、`surveyPhase`、`slipPhase` 位于 `frontend/depot.js`。账号权限见 `backend/domain.py` 与 `frontend/base.js`。许可证见 [LICENSE](LICENSE)。

## 批次、同意与到点交接

- **批次拣配**登记送达库房的批号、保质日与实收件数。草案按计划到点日使用 FEFO（先到期先分配），允许为同一种物资跨批取数。草案锁定一份候选拣配单，审批时再次核对有效期、批次余额及保留库存；库房旧散存仍可按原流程出库。
- **备选换品**要求原组合和替代组合来自同一次 Eclat 场次，只改变一个等箱规物资。拿到点位同意后把替代品草案关联原需求，审批按原申报量抵扣并按实际供应物资扣库存。
- **到点点收**只接收已出库单。点位上报两种物资的实点件数，复核时短少必须标为运输损失或待转运。短少凭证保留库存变动依据，系统不假定缺件已回库。
